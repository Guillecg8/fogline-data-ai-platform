# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this repo is

`fogline-data-ai-platform` is a portfolio monorepo for a **fictional** company, Fogline Hospitality
Group (hotels and restaurants). It exists to show senior-level Data & AI engineering to hiring
managers at early-stage startups: scalable data infrastructure (Medallion pattern) plus foundation
models grounded on proprietary data. Every design choice should be defensible in an interview.

Constraints that shape every decision:
- **Cost ≈ 0.** No paid APIs or cloud by default. LLMs run locally with Ollama (`qwen2.5:7b`).
- **Development happens in WSL2 (Ubuntu) on a Windows machine**, inside `~/projects/fogline-data-ai-platform`
  (never under `/mnt/c`: slow and permission problems). Commands are bash. Windows App Control (Smart App
  Control) blocks unsigned executables such as `.venv\Scripts\python.exe` on the owner's Windows side, so
  local Windows execution is not available. CI runs on ubuntu and windows, so code must stay portable.
- **All data is synthetic**, generated by code in this repo. Never add real data, real names or secrets.
  One narrow exception: P3 may use public Open Food Facts product data (ODbL, with attribution),
  restricted to a field allowlist that excludes contributor fields and any other personal data.
  Adversarial or injected text goes only in fictional fixture products, never attached to real OFF
  products or brands.
- **Short timeline.** Prefer the smallest change that proves the point. Do not add scope silently.

## Commands

Everything goes through `uv` and `poe`. Run from the repo root in the WSL terminal (bash).

```bash
uv sync --all-packages        # needed so every workspace member is installed
uv run poe check              # ruff check + ruff format --check + pytest. MUST pass before any commit
uv run poe format             # ruff fix + format
uv run poe test               # pytest only
uv run poe lh-all             # P1: generate, ingest, silver, gold, verify
uv run poe lh-benchmark       # P1: full rebuild vs incremental, writes BENCHMARK.md
uv run poe eval-all           # P2 evals (needs Ollama reachable)
```

Other P1 tasks: `lh-generate`, `lh-contracts`, `lh-ingest`, `lh-silver` (incremental by default,
`--full` rebuilds), `lh-gold`, `lh-verify`. Other P2 tasks: `ingest`, `search`, `ask`, `mcp`,
`mcp-demo`, `eval-retrieval`, `eval`, `eval-report`, `mcp-lakehouse`.

`uv` workspace members are `projects/*`. Root `pyproject.toml` holds ruff, pytest and poe config.

## Conventions

- Python 3.12, `ruff` line length 100, rules `E F I UP B`. Run `uv run poe format` before `check`.
- pytest uses `--import-mode=importlib`. Tests must be deterministic and run offline, with no network and
  no LLM calls (LLM-dependent quality is covered by saved eval results and CI gates, not live calls).
- Type hints on public functions. Small modules with one job. No dead code, no commented-out code.
- Commits: Conventional Commits (`feat(p1): ...`, `fix(p2): ...`, `docs: ...`, `test: ...`, `chore: ...`).
  One logical change per commit. Never commit generated data, `.venv`, `data/` outputs or secrets.
- `uv.lock` is committed. If dependencies change, commit the lock file in the same commit.
- READMEs and docs in English (they are for SF hiring managers). Chat with the owner is in Spanish.
- Any claim in a README (numbers, speed-ups, accuracy) must come from a command in this repo that the
  reader can rerun. Report numbers measured on the owner's machine, including unflattering ones.

## Portability rules (Windows CI and the owner's Windows history have already broken things)

1. **Do not depend on `pyarrow.parquet` or `pyarrow.dataset`.** They were blocked on the owner's Windows
   machine and the code is written without them. Read Delta with `deltalake.QueryBuilder`
   (`delta_io.read_arrow`), write with `write_deltalake`, merge with `DeltaTable.merge`. No
   `pandas.read_parquet`, `DeltaTable.to_pyarrow_table()` or `to_pandas()`. `pandas` and `polars` are not
   installed. Moving data between DuckDB and Arrow in memory is fine.
2. **Windows thread stack is 1 MB.** Huge SQL `in (...)` lists crash DataFusion with "stack overflow"
   (it passes on Linux and fails on Windows CI). Use `delta_io.read_where_in` (chunks of 100).
3. **DuckDB:** use `.fetchall()[0][0]`, not `.fetchone()`, to avoid "unfinished result" errors.
4. Use `pathlib` for paths. Never hardcode `/` or `\` separators or shell-specific commands in code.
5. Any new test that exercises a blocked module must simulate the block in a subprocess
   (`sys.modules['pyarrow.parquet'] = None`).
6. Node tools on the owner's network may need `NODE_OPTIONS=--use-system-ca`. Do not disable TLS verification.
7. **Ollama** runs on the Windows host. From WSL it may need the host address instead of `localhost`.
   If an LLM call cannot connect, report it. Do not install models or change the default model.

## P1 architecture rules (do not break these)

- Landing files → **Bronze** (raw `_payload` + metadata `_batch_date`, `_source_file`, `_file_sha256`,
  `_line_no`, `_ingested_at`, `_contract_version`, `_row_errors`) → **Silver** → **Gold**.
- Data contracts are YAML under `contracts/`. A compatible change loads, a breaking change quarantines the
  batch. The batch ledger makes ingestion idempotent and supports replay with a newer contract.
- Silver incremental must produce **exactly** the same tables as a full rebuild. Test this whenever
  Silver logic changes. The incremental path reuses the same SQL constants as the full rebuild.
- Gold tables are validated against `contracts/gold_kpis.yaml` before they are published.
- `lh-verify` compares Gold with the generator's ground truth. It must report a match on all venue-days.
  If it does not, the pipeline is wrong, not the check.
- POS business day starts at 04:00 America/Los_Angeles. Keep timezones explicit.
- Sources are declared in `sources.py`. Adding a source means a `Source` entry, a contract, a generator,
  Silver SQL and tests, never special cases in shared code.

## P2 architecture rules

- Answers must cite sources. If retrieval finds no support, the copilot says so instead of guessing.
- Quality changes need evidence: run the held-out evals and record results in `evals/results`. Model,
  prompt or retrieval choices go in an ADR under `docs/decisions/`.
- The MCP server exposes `search_documents` and `query_kpi`. `OPS_COPILOT_KPI_DIR` selects the KPI source
  (sample or P1 exports). Keep tool schemas stable.

## How to work

1. **Plan before coding** for anything touching more than one module. State the plan, list files you will
   change, and wait for approval when the change is architectural.
2. Make the change, add or update tests, then run `uv run poe check`. Do not report done until it passes.
3. If a command fails because of the environment (certificate, missing Ollama, permissions), stop and
   report the exact error instead of working around it with hacks.
4. Never run `git push`, `git reset --hard`, `git clean`, force operations or delete data directories without
   being asked. Propose git commands; the owner runs them.
5. Keep changes small and reviewable. Prefer editing existing modules over adding parallel ones.
6. When finished, report: what changed, what you ran and the result, and anything left undecided. Do not
   recap the steps.

## Definition of done

- `uv run poe check` passes (lint, format, tests).
- For P1 changes: `uv run poe lh-all` also passes end to end on a clean data directory.
- README and docs updated if behaviour or numbers changed. ADR added if a significant decision was made.
- No generated data, caches or secrets staged (`git status` is clean except for intended files).
